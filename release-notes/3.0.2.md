# TPS Finances 3.0.2 — Late GCM menu readiness

Backward-compatible dependency startup correction; minimum Obsidian remains 1.12.0.

Finances previously attempted its GCM **Open finances** menu registration only
once during `onload`. If GCM became ready afterward, the action remained missing
until Finances reloaded. Finances now subscribes to the existing
`tps:gcm-api-changed` workspace event before its initial API lookup.

Only matching GCM packets with explicit boolean availability are accepted. A
missing API in an available packet, malformed or unrelated packets do not alter
the owner. One transient API identity and the existing removal callback own the
registration. Repeated announcements for that same API are no-ops. Replacement,
unavailability and Finances unload clear the owner before invoking its removal
callback. Old cleanup runs before new registration because GCM removes actions
by their plugin/action key rather than registration identity. Unavailability
does not re-read the still-discoverable old API during GCM unload. A failed
registration leaves no stale owner; a later valid announcement can register.

The existing action's label, icon, order, current Finance-record/folder visibility
and dashboard click remain unchanged. Readiness and cleanup do not enumerate or
read notes, rebuild a dashboard model, call a provider, change settings or write
notes. There is no poller, retained data cache, import, new persisted setting,
schema migration or public API change. This is dependency correctness, not an
installed-device performance or UI-latency claim.

## Validation

- Actual complete Finances source is bundled in memory and its real `onload`,
  registration helper and `onunload` execute against a small mobile Obsidian/event
  facade. Layout callbacks are registered but never executed. All source,
  metadata, inventory, mutation, settings-write, model and provider operations
  are blocked during readiness and cleanup. Existing action visibility checks
  use synthetic metadata, and its click uses a presentation-boundary stub.
- The initial 11 regressions produced eight expected failures and three passes
  before source changes. With malformed matching-packet and failed
  registration/cleanup controls added, the unchanged 3.0.1 source produced ten
  expected failures and four passes. The candidate passes all fourteen, including
  cleanup-before-replacement using a faithful key-deleting callback facade, both
  load orders, same-API repeats in both orders, provider unload/reavailability,
  listener disposal and unchanged action behavior.
- The focused readiness/mobile suites pass all 21 checks. The existing mobile
  harness now supplies Obsidian's workspace event-registration boundary; it does
  not exercise a real mobile installation or provider authorization.
- Versioned `TPS_NO_DEPLOY=1 npm test` passes all 419 checks (2 connection and
  417 Finance), with no failures, cancellations or skips; its TypeScript-checked
  bundle build reports `target=none reason=TPS_NO_DEPLOY`.
- A separate `TPS_NO_DEPLOY=1 npm run build` passes after the README changes with
  matching artifacts. An ordinary final TypeScript-checked build deploys only
  `main.js` and `manifest.json` to the exact Test vault; `styles.css` is unchanged.
  Finance `data.json` remains byte-identical. Production was not accessed.
- The actual installed 3.0.1 lifecycle passed four of eight isolated checks and
  failed late readiness, replacement, unload-unavailability and reavailability.
  After targeted reload, exact loaded 3.0.2 lifecycle methods pass all eight.
  These run on independent event/registry hosts with the actual loaded method
  implementations, not by patching live methods or broadcasting live events.
  Source, metadata, inventory, mutation, settings-write, model, provider and
  layout-execution counts stay zero. The eight active plugins' settings, data,
  artifacts, enabled/loaded state and the live lifecycle method identities are
  preserved. Commands, layout callbacks and views are not invoked by this probe.
- The separate actual target reload confirms one real GCM Finances action and
  twenty subsequent same-API helper calls with zero new registrations. All eight
  plugins' settings/data and enabled state are preserved. The first QA command
  stopped before reload because its optional-data guard assumed Messager had a
  `data.json`; correcting that scratch-only guard allowed acceptance to proceed.
  This was a probe precondition error, not an application failure.
- The window is hidden/unfocused. This proves loaded lifecycle registration
  correctness, not foreground input-to-paint latency, a physical phone/Windows
  measurement, cold-process responsiveness or provider-import acceptance. Final
  documentation rebuild preserves the hashes below. Publication is the user's
  BRAT handoff; it does not install the release in production.
