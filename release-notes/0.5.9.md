# TPS Finances 0.5.9

TPS Finances `0.5.9` is a backward-compatible transaction-storage performance and reliability release. Ordinary and investment transaction batches reuse one invocation-local Markdown index on the normal path, reconcile only known or touched files between writes, and discard the index at the public batch boundary.

## What changed

- `applyTransactions()` and `replaceInvestmentTransactions()` retain one lazy transaction index for their own sequential batch instead of invalidating it after every successful mutation.
- Every successful `Vault.process()` supplies the exact committed note text. TPS Finances reparses that touched file directly, including transaction records added by a template or concurrent edit, without another vault read.
- Before consuming an already indexed transaction's local metadata or removing its old copies, TPS Finances refreshes only its known source paths.
- If a known source disappears, moves, changes path during its awaited read, is replaced at the same path, or no longer contains the expected record, the invocation snapshot is invalidated and rebuilt once before the current transaction continues. This is a bounded correctness resynchronization, not an alternate write route or retry.
- Target-note content is reconciled inside the atomic `Vault.process()` callback, so a `categoryOverride` or tags added after the initial batch snapshot are retained.
- The index keeps explicit vault-file order and line order. Touched-file replacement removes old path records, indexes all current transaction lines, and sorts each affected ID once.
- The complete index is cleared in `finally` after success or failure and is never retained across the ordinary-to-investment network gap, institutions, Syncs, or plugin reloads.

## Preserved behavior

- Removals still run first, modified transactions second, and added transactions last.
- Added and modified counts remain input counts, including the released invalid-date skip behavior. Removed count remains the number of mapped finance IDs found, not a line or file count.
- First-vault-file and first-line local metadata precedence remains unchanged.
- Same-file and cross-file duplicate cleanup, destination-before-source routing, daily-note/account-note ownership, transaction line order, local category overrides, normalized tags, and investment fields remain unchanged.
- Every write remains sequential and uses Obsidian's supported atomic `Vault.process()` API. Failures propagate once without rollback, retry, alternate routing, or fallback writes; previously committed work remains idempotently retryable.
- Empty batches, unmapped removals, and invalid-date-only batches still perform zero transaction-index scans.
- Commands, settings, Plaid requests and cursor/watermark ownership, device state, financial note formats, classification, budgets, snapshots, dashboard behavior, GCM/Daily Notes integration, and minimum Obsidian `1.12.0` are unchanged.
- No settings or data migration is required.

## Before and after evidence

- Untouched exact public `0.5.8` is pinned by version, peeled commit `a2cd5f7c7d6ff65c37a75dbb79a480ac7d1ec85d`, clean worktree, and `src/finance-store.ts` SHA-256 `036fd8bd6346e3ee6ee67bbf272f21716efa37048eeb9818af32de1b9bffd48f`.
- Exact `0.5.8` passed all 49 release checks, TypeScript, and its production build.
- The new before-source gate failed only the intended optimization condition: 80 valid writes across 2,000 Markdown files caused 80 full traversals and 160,000 cached reads instead of one traversal and 2,000 reads.
- The final candidate passes 17 permanent transaction-batch tests without an external baseline worktree. When the exact baseline is supplied, the same 17 tests execute real released and candidate `FinanceStore` bundles and assert either exact equivalence or the one intentional replacement-race reliability improvement.
- The exact-equivalence comparison covers dense removal/modification/addition ordering, repeated IDs, same-file and cross-file duplicates, daily/account routing, local metadata precedence, investment records, generated target templates, touched-note concurrent edits, known-source edits and renames both between writes and during an awaited read, target metadata added after the snapshot, missing-source invalidation, every resolver/write failure position, initial-index failures, and failed-call retries.
- In the same-path replacement race, released `0.5.8` commits metadata from the stale pre-replacement read. Version `0.5.9` detects the changed `TFile` identity, builds one current supported-vault snapshot, commits the replacement metadata, and removes the current source copy.
- In the deterministic 20,000-file/500-change fixture:
  - exact `0.5.8`: 500 Markdown traversals, 10,000,000 cached reads, 500 atomic writes, 12.557 seconds;
  - final `0.5.9`: one Markdown traversal, 20,000 cached reads, 500 atomic writes, 0.253 seconds.
- That fixture removes 99.8% of the full-vault traversals and cached reads. Structural call counts are the acceptance gate; wall-clock timing is informational and depends on vault contents and hardware.
- A one-item modification or removal performs the same one full traversal as `0.5.8` plus one supported read of its known source. That bounded read intentionally closes concurrent local-metadata and rename/replacement windows; this release's speedup claim is for multi-item Sync batches, not singleton changes.
- A synthetic second-index read failure stops released `0.5.8` after its first committed item. Version `0.5.9` completes both items because that redundant read no longer exists; it does not retry or switch routes.

- The final versioned declared suite passed 66/66 checks, followed by TypeScript and the suite production build.
- Two independent adversarial reviews found and blocked stale known-source edit and rename cases in the first candidate. The final candidate adds bounded known-path refresh, missing-source reindexing, and atomic target reconciliation; both reviewers then rechecked the corrected implementation.
- A mandatory separate final `npm run build` passed and deployed only byte-changed plugin artifacts to the isolated test runtime.
- Obsidian 1.12.7 was reloaded in `Obsidian Plugin Test Vault`; the disconnected Finances dashboard and registered commands were checked without connecting Plaid, syncing, changing settings, or mutating finance notes.
- Test-runtime `data.json` remained absent.
- Production was not accessed or promoted.

## Known limitation

TPS Finances remains intentionally single-writer during Sync. A brand-new finance marker independently inserted into a different note that was neither indexed nor touched after the batch snapshot remains untouched and becomes visible to the next batch or fresh read. Adding global listeners or per-item fallback scans to observe that unsupported multi-writer race would materially increase state and complexity. Edits to every known or processed transaction note are refreshed or reconciled before their record is consumed or removed.
